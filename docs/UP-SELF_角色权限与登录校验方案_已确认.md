## 1. 建议确认的总体方案

1. 三个业务角色：学生 `student`、导师 `mentor`、平台管理员 `platform_admin`。每个账号先保留一个主角色。
2. 沿用两个认证入口：学生入口 `/client/login`；导师和管理员共用 `/empLogin` 及 `/empLogin/totp`。一个网站可以有入口选择，不需要拆成三个服务。
3. 保留 Spring Security、项目原有 JWT/Redis 登录态、菜单权限和 `@ss.hasPermi`，不新增认证框架或中间件。
4. 学生用本项目账号密码；导师和管理员用账号密码加参考已有 TOTP 动态码。首版由管理员创建账号，不开放注册。
5. 每次业务访问依次检查：是否登录 → 是否有操作权限 → 是否有对应课程/记录/文件的数据权限。
6. 心情默认仅本人可见；只有明确分享给指定导师的内容，指定导师才能查看。平台管理员不默认读取个人心情或学生作业正文。

以上第 1、4、6 项中的具体业务选择需要确认；底层框架版本和参考实现不变。

## 3. 三种角色与账号管理

| 角色 | 使用范围 | 明确不授予 |
|---|---|---|
| 学生 `student` | 已加入且有效课程、自己的进度/提交/反馈/心情 | 教学管理、他人作业、他人心情、角色分配 |
| 导师 `mentor` | 自己负责课程的资料、作业、批改、公告，以及明确分享给自己的心情 | 其他导师课程、全站账号管理、修改学生心情 |
| 平台管理员 `platform_admin` | 账号启停、角色分配、课程创建、师生分配、平台内容管理和运行记录 | 默认读取个人心情/作业正文、冒充学生提交、冒充导师评分 |

**业务适配、待确认：**一个学生可加入多门课程，首版每门课程一个负责导师。导师与学生通过课程关联，不额外创建“班主任”“心理咨询师”等角色；心情分享必须指定具体导师，不能因为授课关系自动开放给所有导师。

**沿用：**保留 `sys_user → sys_role → sys_role_menu → sys_menu`，菜单类型继续 M/C/F。学生权限也加载到 LoginUser.permissions；可以没有复杂的学生动态菜单界面，但后端接口仍执行同样权限检查。

**管理员特别约束：**日常平台管理员不能使用参考超级管理员的 userId/roleId 特殊值，不使用 roleKey=`admin`，不默认取得 `*:*:*`。如保留参考超级账号，仅供初始化和维护，不能作为日常平台管理员账号。业务 Service 的敏感数据校验不因超级账号自动跳过；能直接访问数据库的运维人员仍具有基础设施访问能力，不能宣称本方案能限制数据库管理员。

首版管理员只可分配三个已批准角色，不能通过用户编辑、角色编辑、菜单授权接口给自己新增通配权限。系统字典、菜单、数据库监控等原后台功能按实际需要授权，不整包开放。角色停用、用户停用、密码重置、角色变更均应影响已有登录态。

首批平台管理员由独立项目初始化流程建立；其他账号由管理员建立。密码散列、绑定密钥和账号数据全部独立，不导入参考用户。改密入口复用原用户管理模式；“首次登录强制改密”不假定参考已存在，若要强制实施再列为独立小需求。

## 6. 登录与会话流程

### 6.1 学生入口：保留客户端链，替换 CRM

**业务适配：**`/client/login` 接受毕业项目账号密码，查询毕业项目自己的用户库；确认账号正常且主角色为 student。角色错误不得创建 token。前端传 roleId、userId 或“管理员”选项都不能决定身份。

学生采用参考后台已验证的本地密码处理规则：后端将原密码转小写 MD5，再由 BCrypt 校验；存储结果为 `BCrypt(MD5(password))`。创建、登录、修改和重置必须一致，前端不能再重复 MD5。上线通过 HTTPS 传输，MD5 预处理不等于传输加密。

沿用 LoginUser、权限装载、SecurityContext、JWT 和 Redis 模型。客户端内部 authority `crm` 更换为本项目学生标识，建议 `student`；客户端令牌使用独立的 token 配置和 Redis 命名空间。客户端原来的 CRM token、签名参数、Cookie 兜底、CRM 查询和外部信任必须移除。

**与参考客户端的差异必须明示：**原 ClientTokenService 存在 CRM 绝对缓存过期语义，不能声称已经具有本地学生账号的 120 分钟滑动续期。毕业客户端在原 TokenService 模式下适配本地登录态，建议统一 120 分钟滑动有效期；同时装载 permissions，才能让学生接口使用同一 `@ss.hasPermi`。这部分在确认后实施并验证，不在本次编写。

### 6.2 导师与管理员入口：保留后台两步登录

1. `/empLogin` 校验账号、密码、账号状态以及角色必须为 mentor 或 platform_admin。
2. 密码通过后，已绑定者返回 `needTotp + ticket`；未绑定者返回绑定所需信息和 ticket，按参考流程完成首次绑定。
3. `/empLogin/totp` 校验 ticket 和动态码，并重新核对账号状态及允许登录的角色。
4. 两步成功才签发正式 token。ticket 不是登录 token，不能访问业务接口。

**沿用：**ticket 5 分钟、一次性使用；时间片防重放；绑定完成后保存加密密钥。TOTP 服务及加密配置生成毕业项目独立密钥，不能使用参考密钥。动态码需校时，不新增短信服务。

后台链的 authority=`admin` 只代表管理端身份，mentor 和 platform_admin 均可具有它；它不表示超级管理员，实际业务能力由 permissions 决定。学生 token 不能跨到后台；后台 token 也不自动进入学生接口代学生操作。

TOTP 重置沿用原管理方式并撤销目标登录态；普通管理员不得随意重置其他管理员验证器以接管账号。管理员自身遗失验证器的恢复由维护账号进行，首版不增加邮件/短信找回。

### 6.3 失败限制与验证码

**沿用 S02/S03/S13：**账号错误计数窗口 10 分钟、阈值 5 次、达到阈值锁定 30 分钟；密码和 TOTP 错误共享计数，使用原 Redis Lua 原子方式。不是简单地“任何 5 次错误永远累计”。学生本地密码入口复用此方式，避免新入口成为绕过点；沿用现有 IP 限流组件，不新增限流框架。

**事实边界：**参考 `/empLogin` 虽接收验证码参数，实际有效流程未调用现成的 validateCaptcha，不能写成已强制图形验证码。首版建议不额外接入图形验证码，先保留既有限流、锁定与后台 TOTP。

### 6.4 token、续期和退出

**沿用 S05：**JJWT HS512 签名，JWT 携带登录 UUID，真实用户及权限存 Redis；不是每次只凭 JWT 载荷离线信任身份。参考签发代码没有设置 JWT exp，是否有效取决于 Redis 登录态。

- 请求头采用 `Authorization: Bearer <token>`；不把 token 放在 URL。
- 每次有效认证请求刷新为 120 分钟；无请求 120 分钟后登录态过期。不是“登录后固定两小时必退出”。
- 沿用 `/logout` 和 `/client/logout`；服务端删除对应 Redis 登录态，前端清理持有的 token。
- 密码重置、账号停用/删除、主角色切换：撤销该用户两个入口的全部登录态；TOTP 重置也撤销后台登录态。
- 单纯菜单权限变化：沿用在线权限刷新机制；实施时验证已登录学生和后台用户都能立即失去被撤销权限。
- 课程退出、导师更换、分享撤销：每次请求查当前关系/分享状态，不靠 token 缓存授权，因此不必等 token 过期。
- 首版沿用可存在多个登录态的方式，不增加单设备登录、refresh token 或第三方 SSO。

以上撤销策略包含必要业务补齐，不能因为参考有 kickOutByUserId 方法就断言所有管理调用点已接好。实施时必须逐个验证。

|---|---|
| 学习内容 | 当前课程有效、内容已发布、学生有有效加入关系；导师需当前负责 |
| 学习进度 | owner 为当前 student；禁止从请求直接取可信 studentId |
| 作业提交/附件 | 学生本人提交，或当前负责该课程的导师；还需校验任务属于该课程 |
| 评分 | 当前导师负责提交对应课程、提交状态允许批改；评分作者取当前登录用户 |
| 公告 | 阅读有课程关系；导师修改还需本人作者；管理员下架记录真实操作人 |
| 心情 | 本人，或者当前指定导师且有效分享；不返回未分享字段 |

学生 A 更换请求中的 studentId、submissionId、fileId，也不能获取学生 B 的内容。列表、详情、统计、下载、修改、删除和导出全部执行同一范围，不能只保护列表。

**文件必须纳入同一鉴权：**数据库保存资源归属及用途；上传时从登录态确定所有者，绑定提交时核对所有者和目标作业。作业与心情相关附件不得通过永久公开静态 URL 绕过权限。复用既有上传/OSS能力，但敏感文件使用后端校验后的下载，或现有存储能力支持的短时授权链接。短时链接签发后在有效期内仍可能使用；撤销授权需要立即生效的敏感下载优先走后端鉴权。具体采用哪个存储后端仍按已确认部署方案，不在此新增供应商。

上传/下载大小、类型校验沿用原校验组织方式；不得把参考公开上传白名单或原业务开放路径直接复制到新工程。

## 8. 每周心情的授权规则（已确认）

- 时间按 Asia/Kuala_Lumpur，周一 00:00 到下周一 00:00；每人每周一条，本周可修改，历史只读。日期和归属由服务器计算。
- 默认本人可见；首版分享采用“指定导师＋明确周记录”，不自动共享未来所有记录。
- 建议将“分享分数/趋势”和“分享文字备注”分开：默认备注不分享，学生明确允许才返回。趋势只含实际授权周的点，未授权或未填写周不插值。
- 学生可撤销分享；下一次后端请求即拒绝读取。无法让对方已看见或自行保存的内容消失，不做此类承诺。
- 导师被取消关系/停用，分享访问随之失效；更换导师不会将历史分享自动转交新导师。
- 管理员可以处理账号或系统故障，但首版不提供查看心情全文的管理功能，不建立“紧急情况下自动放开”的隐含后门。
- 图表展示每周自评变化，不进行诊断、自动预警或向其他人自动推送心情信息。

这套分享边界是业务建议，不是参考项目已有心理数据模块。若你希望“首版导师完全不看心情”，可以取消分享入口，保留学生本人趋势，底层认证方案无需变化。

## 9. 前后端响应约定

沿用 AjaxResult、ServiceException 和现有全局异常处理，不建立第二套响应协议。

| 情形 | 处理要求 |
|---|---|
| token 缺失、无效或 Redis 登录态消失 | JSON code=401；清理前端登录态并返回对应登录入口 |
| 已登录但缺少接口权限 | JSON code=403；显示无权访问，不误当成密码错误 |
| 课程/记录不在授权范围 | 统一使用现有无权限/资源不可用响应，不泄露他人记录细节 |
| 密码错误、锁定、ticket 失效、动态码错误 | 使用参考已有对应业务错误码和信息，不借用 401 处理全部失败 |
| Redis 不可用 | 登录/鉴权失败并记录系统异常，不能降级成匿名放行 |

S11 当前未认证响应 HTTP 为 500、JSON code 为 401；S12 方法权限异常通常 HTTP 200、JSON code 为 403。第一版严格沿用该事实，前端同时处理非 2xx 响应体里的 code，不能只监听 HTTP 401/403。过滤器链拒绝与方法权限拒绝仍需分别联调；不得在文档中把所有 HTTP 状态声称一致。若之后需要规范 HTTP 状态，应另行明确最小修正，不能顺带重写异常体系。

日志沿用登录日志和业务操作日志；记录账号、操作、目标 ID、结果，不记录密码、token、动态码、绑定密钥、心情备注或作业正文。登录/TOTP 请求和响应不得被通用参数日志原样记录。
